Automation is not new for us. Long before AI was a conference topic we were writing MAXScript to solve production problems — CAD import cleanup, batch render submission, scene organisation scripts that save hours per project. One example that has held up: CAD import preparation used to take 30–45 minutes per project; a MAXScript tool we built cut that to under five. Over dozens of projects a year, that is real time recovered.

What has changed, twice now, is the tooling around that work. First AI assistants made scripts far faster to write and debug. Then, this year, the assistant stopped needing us to write the script at all for many jobs — it drives 3ds Max itself, through a tool server we built for it.

## Stage one: AI writes the MAXScript

**Code completion and generation.** Describing a workflow in plain language and getting a working first draft saves the hour that used to go into scaffolding. It still needs review and a test on a real scene, but the starting point is much closer to finished.

**Error diagnosis.** Pasting a failing script into an assistant surfaces the problem faster than reading it line by line — off-by-one errors, missing property checks, a loop that never ends.

**Optimisation.** For scripts that run on large scenes, AI-suggested refactoring has meaningfully cut execution time: one production script went from a ten-minute run to under three.

**Tools that were never worth writing are now worth writing.** A script that took two days to build and debug takes hours. That moves the threshold: a step that happens on every project and that a person gets wrong on the sixtieth repetition is now worth automating even if it saves only minutes each time.

The result of a few years of this is [the toolkit we built for ourselves](/articles/the-3ds-max-toolkit-we-built-for-ourselves/): a procedural building generator, a batch camera renderer, sun and camera utilities, a garden planner — about 20,000 lines of MAXScript and 16,000 of Python, in daily use here.

## Stage two: AI operates 3ds Max

Writing a script and running it is still a loop with a person in the middle: describe, generate, paste, run, read the error, repeat. The next step was to remove the paste.

We built an MCP server for 3ds Max — a tool server that exposes the application to an AI assistant as a set of typed operations, currently about 115 of them. Scene inspection and selection, object and modifier properties, material networks and texture maps, RailClone and Forest Pack styles, tyFlow events and operators, OSL shaders, state sets, viewport captures, batch renames, layer management, merges from other files. The assistant calls those tools the way it would call any API, and sees the result — including a screenshot of the viewport — before deciding what to do next.

What that looks like in practice:

1. **"Tell me what's wrong with this scene."** The assistant walks the hierarchy, lists objects with missing textures or absurd scale, reads the render settings, and reports — in seconds, on a scene with thousands of objects.
2. **"Set up the background street like the last project."** It creates the RailClone and Forest Pack objects, assigns the styles and materials, scatters along the splines we point it at, and captures the viewport so we can check.
3. **"Rename every camera to the sheet, set resolutions from this table."** Tedious, error-prone by hand, one instruction now.
4. **"Write me an OSL shader that does X."** It writes the shader, creates the map, assigns it, renders a test frame, and iterates on what it sees.

**The tool is deterministic; the assistant is not.** Every operation the server exposes is plain MAXScript or Python underneath, doing one named thing. The assistant decides *which* operations to call and in what order — and we watch it, the same way we would watch a new colleague on their first day. Nothing it does is invisible: the scene is right there.

## Where this connects to the rest of the pipeline

Rendering is only half of a picture now. The working render that leaves 3ds Max goes into [our AI finishing pipeline](/articles/from-render-to-photograph-archupgrade/), and that system, too, is driven by tools rather than by hand: scripted ingest of render passes, structured prompts assembled from per-camera metadata, automated review. The same discipline — deterministic tools, an assistant choosing among them, a person at the end — runs from the first CAD import to the delivered image.

## What AI doesn't replace

Understanding what problem you are actually solving is still the human's job. An assistant produces plausible scripts that do not always do what you intended; testing against real project files, handling edge cases, and knowing when a tool is causing more problems than it solves — that is experience.

Production scripting is tied to specific workflows. The assistant does not know that our render manager needs output paths in one particular form, or that a client's files always arrive with a naming convention that needs cleanup, until we tell it — and then it needs telling again next session. That institutional knowledge lives in the tool definitions we write, which is one reason the MCP server exists.

And a script — or an agent — is the wrong answer more often than script authors admit. If a task will happen twice, do it twice.

## The honest position

MaxScript is still the right tool. It reaches virtually everything in the application — object properties, render settings, material parameters, scene structure — and that depth is exactly what makes a tool server useful: every one of those 115 operations is a few lines of MAXScript with a typed contract on top. What changed is who writes the lines and who runs them.

The assistant gets things wrong. It has renamed the wrong objects, clobbered a live variable with a two-letter name, and cheerfully replaced a template placeholder with literal text. That is why every tool it can call is narrow, why the scene stays visible, and why nothing it does is a substitute for the lint gate and smoke tests that guard the scripts real work depends on.
